# Split Tickets

Create useful implementation units that fit a fresh context through understanding, implementation, verification and repair—not a new production design.

Before investigation, questions or drafting, read the complete [TICKETS.md](TICKETS.md) and `artifact-layout`. Load reference skills by registered name through the harness; resolve stage-local files relative to this installed skill and cross-skill content through its registered owner, never guessed configuration paths; reuse intact current supplied content. Standard imports do not load the owner's SKILL or workflow prerequisites. Missing required sources block work. Load registered `ask-with-context` when a substantive human question is needed; read [reviewer-prompt.md](reviewer-prompt.md) at review dispatch.

Read `review-records` before the first submission or record creation, before finding-linked repair, or when recovering relevant existing records—not automatically for fresh clarification. Layout owns paths, names, exclusion, file purpose and single-writer ownership; records owns admitted evidence and schemas; this stage owns permission and validity.

## 1. Recover the approved basis and roles

Resolve supplied child paths to root `issue.md`. Inspect the complete route-appropriate approved package, current code/callers, project guidance and verification facilities under TICKETS.md. Resume from actual sources, records and evidence, not status labels. Send production-design gaps to their owning authority; a bounded direct change goes to `implement` without synthetic tickets.

Retain the original ticket-plan author and a separate independent read-only reviewer across repairs and resumption. Bind the reviewer at first review. Attempt actual role resumption/context recovery before replacing a genuinely unavailable role; explain the loss and give its replacement current inputs and old findings, preserving the available counterpart. Speed or disagreement never justifies replacement; unavailable independence blocks review. This planning pair is distinct from implementation pairs.

## 2. Construct the coherent set

Map every approved obligation to a useful result, real prerequisite outputs and verification owner. Size units for the whole working cycle; split independent objectives and merge inseparable cutovers or fragments without useful results. Assign integration and every selected macro-flow test to actual implementation/execution owners. Keep speculative splits in the conversation and resolve consequential decomposition choices without reopening settled design.

Prepare one root index and actionable tickets through the specification-authority gate below; confirmed scope does not preauthorize ticket text or execution metadata.

## 3. Review the complete plan

Rehearse the entire dependency order as an unfamiliar implementer. Resolve links and actually render and visually inspect all dependency diagrams. Complete content, current approved sources and mandatory planning evidence are prerequisites to approval; future code results are not.

The assigned plan writer alone persists layout-defined records; the reviewer returns reports without editing. Record the identified submission and actual repair/check evidence in `tickets.review-fix-decisions.log.md` before review and send the complete package specified by [reviewer-prompt.md](reviewer-prompt.md). Save every report before acting or advancement and reviewer dispositions before dependent work or handoff. Findings return to the original author for repair through the specification write gate; the **same reviewer** reassesses the complete current set, prior findings and regressions. Repeat until Pass without findings or blockers. Return incomplete reports to that reviewer; only the reviewer disposes findings, while authors leave repairs awaiting review. Missing evidence or independence blocks advancement, never justifies reviewer rotation or ending an actionable repair loop. Later diffs communicate changes, never reduce review scope. A resumed set needs current independent assessment; an unchanged evidenced human approval may remain applicable.

## 4. Obtain final approval and stop

Present the exact reviewed set, coverage, dependencies, material tradeoffs and repair decisions for explicit final human approval, distinct from direction or repair consent. Revisions return through the original pair and affected verification. Record approval against the set/source identities; any metadata write still needs its exact preview and confirmation.

Return the approved index and essential references, or the precise blocker after reachable authorized work. Stop: approval for later implementation does not launch it. No code, planning-only delivery summary, publication or commits.

## Specification authority and evidence validity

Before **every** creation, edit, move, deletion or reorganization of an entry, model, ticket or canonical specification, the assigned original author must display the exact content/patch, destinations, current basis, deletions and consequences, obtain explicit human confirmation, then apply only that content. This includes metadata, formatting, typos, synchronization, migrations and reverts, without inferred exceptions. A fully displayed multi-file batch may be confirmed once; direction, Pass, authority to work or “continue” never approves unseen text or dependent decisions. Keep unconfirmed proposals conversational, not candidate drafts or log workarounds.

Immediately before applying, recheck both basis and proposed content against the concrete confirmation; either changing requires renewed confirmation. Resumption and delegates must recover that evidence, not remembered consent. Supply prior concrete confirmations to reviewers even for newly written specifications. Final human approval is distinct and binds the exact reviewed result and sources; it may simultaneously approve a fully displayed exact metadata patch. Authorized code-only fixes and factual admitted records bypass this specification gate, but cannot amend specifications indirectly.

Use exact current result/source identities, including relevant dirty/untracked code. Approval/status metadata may stay outside the reviewed digest, or explain a metadata-only difference. Substantive source, result, scope, membership or obligation changes immediately invalidate affected evidence and approval even while status correction awaits permission; preserve unaffected approval only with an actual impact basis. Recover comparison evidence rather than treating a digest as a historical snapshot. For legacy mixed artifacts, require exact migration confirmation and attributable provenance; unknown provenance blocks the affected migration, not unrelated work.
