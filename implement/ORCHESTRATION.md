# Whole-Requirement Implementation: Orchestration Standard

## Authority and scope

Use this same standard while coordinating execution, repairing findings, and independently reviewing the combined result. Load `implement-unit` by registered name in reference-only mode and read its IMPLEMENTATION.md and reviewer-prompt.md from the actual installed location before orchestration. IMPLEMENTATION.md is the single shared standard for source-entry gates, code conformance, TDD, runtime evidence, and persistent unit roles. This standard adds coordination and whole-result delivery. The approved technical target governs production design; review is conformance, not a new design phase or planned cleanup.

Before authoring, resumption, or review, load `workflow-artifacts` by registered name using the Skill tool or the harness's equivalent named mechanism (omp: `skill://workflow-artifacts`) and read its WORKFLOW-ARTIFACTS.md from that skill's resolved installed location. Its private-storage, pre-write exclusion, clean-authority, record, revision, and recovery contract is mandatory. Reuse a supplied complete current standard or verified readable resource with its owning skill identity without recursively loading it; a summary is not sufficient. Missing or inaccessible required standards block affected work; report the exact dependency, without guessing sibling paths or auto-installing.

This resource belongs to `implement`; same-skill companions resolve relative to its installed document under [SKILL.md](SKILL.md). Consult standards without starting their execution steps or spawning roles. The complete named skills `implement`, `implement-unit`, and `workflow-artifacts` need not share an installation parent; the product checkout and `.scratch/` remain separate from all instruction locations. Route upstream decisions to `clarify-change`, `clarify-requirements`, `clarify-technical-design`, or `split-tickets` as applicable, loading by name only for required reference or authorized execution under the existing gates.

Accept either a complete reviewed/human-approved ticket set or one bounded reviewed/human-approved direct change, with user execution authorization. Apply IMPLEMENTATION.md's approved-basis and route-validation rules. A set may reference approved requirements/technical models or an approved change basis. A direct change uses its CHANGE-MODEL path/revision, exact essential references, and synchronized affected canonical model sections; it needs no ticket or ticket-set index. Current reviewed/approved change evidence can supply the complete requirements/technical basis without old separate models or invented historical approvals.

Both routes require `.scratch/<work-slug>/issue.md` as the work entry. On the ticket route that entry also owns the full set index; tickets use `issues/NN-<slug>.md`.

Inspect actual code, rules, source/approval identities, prerequisite outputs, complete target coverage, and real testing means. Confirm evidence-backed bounded direct fit before dispatch. An approval label is not proof of approval or usable prerequisites. Change-basis domain/requirement/design/source conflicts and post-delivery design questions return to clarify-change, not a forced rerun of original clarification. If direct scope no longer fits one bounded cycle, stop affected work for renewed reviewed/human-approved routing and split-tickets decomposition; do not invent tickets or squeeze the scope.

## Execution basis and compact state

Default to serial execution against one identified workspace containing actual prerequisite outputs. Do not infer parallel safety from missing dependency edges: tickets may share files, state, fixtures, or contracts. A direct change has one full-scope pair, not hidden sub-tickets. This workflow introduces no automatic branching, worktree, merge, commit, or deployment policy. Respect any existing project policy and verify actual incorporated outputs before consumers rely on them. Preserve unrelated user work and distinguish it from the authorized change.

Before writing, the controller establishes or verifies the shared contract's repository-local exclusion: actual Git root/exclusion path including worktrees, preserved local rules, no tracked workflow paths, and effective ignore evidence. Reuse the existing `.scratch/<work-slug>/` identity. Keep a compact current recovery map in its `issue.md`, not in a harness-only record or conversation checkpoint. It must identify:

- Source route, authorized set or direct change path/revision, authoritative source revisions, approval evidence, current workspace and code basis.
- Each unit's prerequisites and, for tickets, dependencies; execution status, original implementer/reviewer handles, and last reviewed code identity.
- Findings/blockers with owning unit and governing obligation, verification references, and applicability of prior Pass results.
- Macro-flow ownership/results and final human-acceptance state; the overall reviewer handle for a ticket set, or the original unit reviewer's current full-change Pass for a direct change.

Use the project's existing status vocabulary if available; otherwise distinguish pending, implementing, in review, passed, and blocked. Passed means current independent conformance, not human acceptance. Keep execution states distinct from source/planning approval. Curate current state in `issue.md` and relevant ticket status fields; link to evidence in logs instead of appending reports to canonical models or specifications. Root `issue.log.md` holds overall reviews/acceptance and all direct execution records. A ticket's same-stem `issues/NN-<slug>.log.md` holds its implementation/reviews/repairs/evidence. No separate index, session log, repair file, or state document is needed.

On resumption read `issue.md`, the relevant current sources/tickets, open findings, latest applicable decisions/evidence, and older entries only as necessary. Verify current workspace, source approvals, actual prerequisites, review applicability, and original role handles. Retained records do not make stale code or lost agents current. Locate and resume original roles; use the unit standard's explicit handoff procedure only when necessary. Do not reset issues or mark unfinished units passed because a session ended.

## Bounded roles and communication

The controller owns scheduling, shared basis, role routing, prerequisite readiness, unresolved issues, and whole-result delivery. It is neither code author nor substitute reviewer. Detailed implementation and review reasoning stay with the bound unit pair.

The controller alone writes shared `issue.md` and `issue.log.md`. Delegated implementers supply entries or write only an explicitly exclusive unit log; read-only reviewers return reports and never write logs. Include the shared artifact contract, entry/log references, verified exclusion evidence, and writer ownership in dispatch packages.

Bind one original implementer and one independent read-only reviewer per unit; create the reviewer at first review and retain both through repairs/resumption. Different tickets normally get different pairs. A direct change has one pair for the entire target and final runtime evidence, with no second overall-review role. Route findings unchanged in substance; do not rotate roles for a favorable opinion.

The initial implementer package includes delegated mode, source route and unit identity, exact approved basis and approval evidence, applicable rules, code basis/workspace, prerequisites, full verification responsibilities, and controller return route. Its first review request is intermediate. Follow the unit reviewer contract for required review inputs, accepting an approved change basis without old separate models. Later messages carry changes since the recipient's basis, current snapshot, finding dispositions, renewed evidence, and changed sources. Keep unchanged sources accessible and private author reasoning out of reviewer instructions.

Every worker/reviewer package identifies the target repository/checkout and work identity separately from the owning skills and instruction resources. Supply owners `implement`, `implement-unit`, and `workflow-artifacts`, complete current required content or verified resolved installed resources, and the authorized role. An implementer receives the resolved installed `implement-unit` SKILL.md with explicit delegated execution; reviewers receive reference-only skill loads and their read-only review assignment. Delegated units return to this controller without recursively invoking it or creating a competing reviewer.

The unit standard governs capability loss and explicit replacement handoff; those rules also govern a ticket set's overall reviewer. Reuse reduces setup, not required evidence or full current-scope assessment. Reconsider prior conclusions wherever code or sources changed.

## Progress, repair, and blockers

A unit is ready only when actual prerequisite results exist on the current basis and relevant conformance evidence remains applicable. Preserve ticket dependencies; an implementer completion claim or isolated branch result is insufficient. After a ticket passes, establish usable output for consumers and continue without per-ticket human confirmation. After a direct unit passes, check final-gate applicability below rather than scheduling fictional successor work.

Automatically return implementation violations to the original implementer and renewed evidence to the original reviewer until current Pass has no unresolved findings/blockers. Reassess complete unit conformance and affected interactions after repairs, not only finding IDs. Ask the original reviewer to correct incomplete or inconsistent reports instead of accepting an incomplete Pass.

Before dispatching review, persist the actual implemented result/repair, handling decision and key rationale, affected obligations or stable finding IDs, and fresh verification in the owning log. Save each returned review with stage/unit, round, date, reviewer identity, exact source/code basis, actual verdict, category coverage, findings/blockers, and prior dispositions before dispatching repair or advancing. Preserve failed/blocked outcomes. Authors can report addressed/awaiting review; only the applicable reviewer confirms closure or withdrawal. Disputes remain open with counter-evidence, not silently closed by the controller.

Persist the new disposition and update current state before scheduling dependents or handing off. Before a blocker, role replacement, or session/stage transition, update the recovery entry with current basis, open issues, evidence links, roles, and next action. Record clean implementation results too; do not defer all evidence to final delivery.

For Blocked, retrieve available evidence, restore tools, or satisfy authorized prerequisites without asking humans for repository facts. Follow IMPLEMENTATION.md's design-boundary routes for upstream decisions: change-basis conflicts go to clarify-change; original model-basis gaps go to their owning clarification stage. Ticket dependency/scope defects return to split-tickets; a direct change exceeding bounded fit requires an approved route change and decomposition first. Renew affected reviews/approvals before resuming. Do not add adapters, fallbacks, or production mechanisms to evade blockers.

If another ticket is genuinely ready and cannot conceal or worsen a blocker, continue it; dependents remain blocked. When no authorized work can progress, report precise unsatisfied conditions, evidence, affected units, and required external action. Missing credentials/capability or necessary human decisions are real stops; ordinary repairable findings are not.

No fixed review-round count grants success or lowers the standard. If the same issue persists without new evidence, compare the disputed obligation, current code, and actual result with the original roles. Resolve repository facts and report any irreducible design conflict or unavailable capability. Do not silently loop forever, rotate agents to erase the issue, or ask for approval of a known failing result.

## Code changes and evidence invalidation

Every review and runtime result identifies the code and source basis it covers. Under serial execution, inspect what a later ticket changed before relying on an earlier Pass: unchanged relevant code and assumptions can retain their evidence, while changed obligations, callers, shared state, or integration behavior require renewed affected checks and review. Do not rerun unrelated tickets merely because another file changed, and do not reuse a Pass for modified behavior.

Apply WORKFLOW-ARTIFACTS.md revision integrity: identify every private source with path plus digest or another verifiable local revision; HEAD alone cannot identify ignored sources. For code identify the checkout and relevant dirty/new content as well as any commit. Retain essential commands/scenarios, actual observations, environment/participants/substitutions, limits, and approval decisions locally; transient tool links alone are insufficient. Distinguish planned/executed/failed/passed evidence. Preserve historical outcomes while marking invalidation; hashes do not reconstruct missing historical bodies.

Before a returning original implementer edits, give it the current combined basis and relevant intervening changes. Its retained earlier context is not permission to restore an old file version or erase later ticket/user work. Review its repair in the current surroundings, not against an obsolete isolated snapshot. Serialize writers and review a stable identified candidate; unexpected concurrent changes invalidate the affected assessment until reconciled.

A repair can invalidate previously passed dependent results. Record that, renew affected unit evidence with original roles, and re-establish readiness/completion before delivery. Changed upstream artifacts require their own approval workflow and refreshed dependent unit sources; the controller cannot approve source changes itself.

## Final verification and route-specific review

**Direct change:** implement-unit supplies final combined checks, all approved macro flows, complete target conformance, and a current full-change Pass from the original independent unit reviewer under IMPLEMENTATION.md. That Pass is the final independent assessment; do not dispatch a second overall reviewer, demand a ticket index, or repeat unchanged work for a duplicate review. The controller checks completeness, stable code/source identity, and evidence applicability, not conformance instead of the reviewer. If obligations or evidence are missing or stale, return to the original pair for repair and renewed full-change review. Human acceptance remains the final gate.

**Ticket set:** apply the rest of this section to actual ticket sets only. After all outputs are present, check complete target coverage on combined code: final file responsibilities, runtime collaboration, contracts/data, callers, state/resource ownership, and retirement of superseded paths. Show that local increments compose without unclaimed work or temporary structures. This does not authorize repository-wide redesign.

Run the required project regression checks and every selected macro-flow scenario on the final combined state, using the real participants and approved substitution limits. The runtime-evidence rules in IMPLEMENTATION.md apply. A previously executed assigned flow can count only with an explicit demonstration that the relevant code, participants, configuration, and environment remain applicable. Planned tests, isolated mocks, compile success, and individual ticket Passes cannot establish final collaboration. Mandatory unavailable execution blocks overall Pass and human-acceptance handoff.

Create an independent read-only overall reviewer in a context separate from the controller and ticket implementers, using reviewer-prompt.md. It receives the complete approved set/design and combined change, not a concatenation of local Pass summaries. Retain that overall reviewer across repair rounds. Route each demonstrated implementation/integration issue to the original owner implementer(s); serialize bounded repairs against current code, then obtain renewed affected ticket review and whole-result review. Do not assign a fresh catch-all agent to refactor the feature after the fact. If the original owner cannot resume, apply the documented handoff rules; if no approved owner exists, resolve that upstream.

The controller and overall reviewer apply these ticket-set categories alongside the full shared unit standard:

1. **Authorized and coherent basis:** current source approvals, execution scope, real prerequisites, preserved user changes, and an identified combined code basis.
2. **Complete composition:** every approved obligation has a conforming implementation and owner in the final result; local increments join correctly and obsolete paths are retired as designed.
3. **Ticket closure and continuity:** all tickets have applicable independent Passes without unresolved findings; fixed roles, handoffs, repair routing, and evidence invalidation follow the shared rules.
4. **Current integrated evidence:** required regressions and macro flows establish their promised results on the combined state with truthful real/substituted scope and limits.
5. **Review and acceptance integrity:** the full current result has a complete independent assessment, no reviewer-invented design criteria, and no claim of human acceptance, issue closure, or release without the appropriate authority. Private paths/exclusion, durable findings/decisions/evidence, source/code revisions, and recoverable state satisfy WORKFLOW-ARTIFACTS.md; logs do not override authoritative models.

A demonstrated violation requires `Changes required`, with additional evidence blockers reported separately. Without demonstrated violations, unavailable mandatory evidence yields `Blocked`. Only all applicable obligations satisfied with no unresolved findings or blockers permits `Pass`. The controller cannot aggregate ticket verdicts into an overall Pass itself.

## Human handoff

After current combined verification and the route-appropriate final independent Pass, persist that evidence and verdict in `issue.log.md`. The controller then authors `.scratch/<work-slug>/delivery.md` before asking for explicit human acceptance. Follow WORKFLOW-ARTIFACTS.md's complete summary contract: delivered outcomes/exclusions, final design landing with authoritative references, consequential decisions and basis, actual verification/review and limits, applicable use/maintenance guidance, and acceptance state. Link it from `issue.md`. A direct change uses its original unit reviewer's full-change Pass; a ticket set requires the retained overall reviewer's Pass. Neither route needs per-unit human approvals or reconfirmation of settled design. Delegated units return records to the controller, not whole-work summaries; standalone units follow IMPLEMENTATION.md's explicitly scoped handoff.

Until explicit acceptance, report awaiting acceptance, not accepted. Conformance repairs retain original unit roles and, for ticket sets, the overall reviewer; content changes invalidate affected evidence/review/acceptance, metadata-only changes do not. New change requirements or design choices return to clarify-change. Stop after acceptance or at a genuine external blocker after all reachable authorized work. No automatic commit, merge, push, tracker closure, or release. Execution consumes the approved change result; it does not govern post-delivery design.

Persist explicit human acceptance with its exact scope/basis and faithful decision evidence in `issue.log.md`; update `issue.md` and `delivery.md` afterward. Before a renewed acceptance request, obtain affected fresh evidence/Pass and integrate the summary. The summary is not another design authority or a substitute for process records. Keep the excluded workspace local and retained; never automatically publish, commit, move out, or delete it.
