# Whole-Requirement Implementation: Orchestration Standard

## Authority and scope

Before starting/resuming coordination or scheduling, read this entire standard, the entire IMPLEMENTATION.md from named skill `implement-unit`, and complete WORKFLOW-ARTIFACTS.md from named skill `workflow-artifacts`. Apply the shared loading/resource and reference-only rules. Only dispatch-specific reviewer prompts may be delayed until first use. IMPLEMENTATION.md owns single-unit source validity, code/test/runtime criteria, and unit-specific invocation; WORKFLOW-ARTIFACTS.md owns the shared persistent author/reviewer lifecycle; this standard owns whole-work scheduling, combined verification, and direct-versus-ticket-set final handoff. [SKILL.md](SKILL.md) supplies the ordered controller workflow.

Accept an authorized reviewed/human-approved ticket set or one bounded reviewed/human-approved direct change under IMPLEMENTATION.md’s route gates. Resolve effort/child inputs to the root `issue.md` and its exact selected source package rather than assuming flat files. Inspect code, rules, real prerequisites, coverage and verification means; resolve scoped approval evidence through model metadata and owning object review logs. One root controller owns scheduling for all global `issues/NN-<slug>.md` tickets; child entries define models, with no local controller, ticket pool, state artifact or delivery. Direct work retains its own work entry, not a synthetic index. Route source conflicts or expansion under the unit standard.

Apply **Human-confirmed specification writes** in WORKFLOW-ARTIFACTS.md before every entry, model or ticket mutation, including first creation, repairs, formatting, references and embedded execution/role/status metadata. The controller cannot authorize undisplayed document changes on the human's behalf.

## Execution basis and ticket-owned progress

Default to serial execution against one identified workspace containing actual prerequisite outputs. Do not infer parallel safety from missing dependency edges: tickets may share files, state, fixtures, or contracts. A direct change has one full-scope pair, not hidden sub-tickets. This workflow introduces no automatic branching, worktree, merge, commit, or deployment policy. Respect any existing project policy and verify actual incorporated outputs before consumers rely on them. Preserve unrelated user work and distinguish it from the authorized change.

The controller establishes the shared exclusion gate before writes. Keep `issue.md` limited to definition/navigation, source-package identities, coverage and planned dependencies; it contains no approval-record index. Read each ticket’s compact execution block, planned dependencies, actual incorporated prerequisite code and applicable verification/review evidence to derive readiness. There is no global scheduler/status ledger, duplicate task checklist or recovery snapshot. Direct work uses its approved change package, actual code and implementation reviews without a synthetic ticket or state record.

Use existing project status vocabulary or distinguish pending, implementing, in review, passed, and blocked in the existing ticket’s compact non-normative execution block. Alongside current status retain only the current blocker, original implementer/reviewer handles and applicable evidence/review references; show and confirm the exact update under **Human-confirmed specification writes** before changing it in place, without planned-task duplication or chronological progress. The shared metadata-only revision convention does not exempt any ticket write from prior human confirmation. Passed means current independent conformance, not human acceptance or source/set approval. `implementation.review-fix-decisions.log.md` holds whole-result/direct submissions, outcomes, finding-linked decisions/evidence, and corresponding human acceptance; tickets use `issues/NN-<slug>.review-fix-decisions.log.md`. On resumption apply shared cutover/resumption rules and verify current sources, actual outputs, evidence applicability and original roles before scheduling.

## Bounded roles and communication

The controller owns scheduling, shared basis, role routing, prerequisite readiness, unresolved issues, and whole-result delivery. It is neither code author nor substitute reviewer. Detailed implementation and review reasoning stay with the bound unit pair.

Use WORKFLOW-ARTIFACTS.md’s dispatch and single-writer rules. The controller owns definition changes to `issue.md` and the overall implementation review log. Assign each ticket and review log one writer: its exclusive delegated author or the controller receiving updates. Direct controller and full-scope pair share one assigned implementation review-log writer. Where no ticket exists, that log may carry a compact work/role identity header for the original full-change pair or retained overall reviewer; this is ownership metadata, not a fifth event type or a place for progress, blockers or next actions. Reviewers return reports read-only.

Apply IMPLEMENTATION.md’s initial author package and WORKFLOW-ARTIFACTS.md’s **Persistent author/reviewer lifecycle**. Add the selected scheduling scope, root entry and precise applicable shared/architecture/child source sections, cross-child prerequisites, combined code basis, actual prerequisite outputs, assigned verification, explicit delegated authorization via the resolved `implement-unit` SKILL.md, and controller return route. Supply the bounded read set, not the whole effort archive. For a delegated specification write, supply its exact shown/confirmed content, current basis and confirmation reference; execution scope alone is insufficient. Authors read complete applicable standards and approved sources **before choices or edits**. Review requests are intermediate; first reviewers receive the full prompt package, later rounds the incremental package. Delegated units create neither another controller nor a competing reviewer.

Each ticket normally has its own pair; a direct change has one pair for its full scope. The shared lifecycle’s genuine-loss replacement rules also apply to the retained overall reviewer. Context reuse does not retain approval of changed code.

## Progress, repair, and blockers

A unit is ready only when actual prerequisite results exist on the current basis and relevant conformance evidence remains applicable. Preserve ticket dependencies; an implementer completion claim or isolated branch result is insufficient. After a ticket passes, establish usable output for consumers and continue without per-ticket code acceptance, after required ticket-write confirmations and persistence. After a direct unit passes, check final-gate applicability below rather than scheduling fictional successor work.

Route ordinary repairs and incremental re-review through the original pair under the shared lifecycle and IMPLEMENTATION.md’s unit criteria. Require full current-unit assessment, not finding-only checks; ask the reviewer to correct incomplete/inconsistent reports. The assigned writer saves identified submissions/verification or finding-linked repair decisions before review, full reports before repairs or gate advancement, and dispositions before dependents or handoff. Show and confirm the exact ticket-status change before writing it; no automatic metadata repair. Before a blocker or role replacement reconcile actual code, evidence, ticket status where applicable and bound roles; carry the missing conditions and handoff basis without a recovery artifact. No ordinary progress diary belongs in review logs. The controller cannot close findings or reinterpret a failed report as Pass.

For blocked work, retrieve accessible evidence, restore tools, or satisfy authorized prerequisites without asking humans for repository facts. Route genuine upstream/ticket defects under IMPLEMENTATION.md; renew affected source/set approval before resuming. Do not evade blockers with invented production mechanisms. Continue other genuinely ready work only when it cannot conceal or worsen the blocker; dependents stay blocked.

Apply the unit standard’s stalled-progress rules rather than rotate roles or lower the gate. When no authorized work can progress, report precise unsatisfied conditions, evidence, affected units, and the required external action. Missing credentials/capability or necessary human decisions are real stops; ordinary code-repairable findings are not. Required specification-write confirmation is a human gate, including document-only review fixes; continue unrelated ready work while awaiting it.

## Code changes and evidence invalidation

Every review and runtime result identifies the code and source basis it covers. Under serial execution, inspect what a later ticket changed before relying on an earlier Pass: unchanged relevant code and assumptions can retain their evidence, while changed obligations, callers, shared state, or integration behavior require renewed affected checks and review. Do not rerun unrelated tickets merely because another file changed, and do not reuse a Pass for modified behavior.

Apply WORKFLOW-ARTIFACTS.md’s source/code revision and evidence-integrity rules to the combined basis, including participating dirty/new code. Preserve historical outcomes while marking affected evidence stale; logs cannot authorize source changes.

Before a returning original implementer edits, give it the current combined basis and relevant intervening changes. Its retained earlier context is not permission to restore an old file version or erase later ticket/user work. Review its repair in the current surroundings, not against an obsolete isolated snapshot. Serialize writers and review a stable identified candidate; unexpected concurrent changes invalidate the affected assessment until reconciled.

A repair or upstream change can invalidate unit and combined evidence. Record the finding-linked impact on obligations, shared contracts/callers, descendants, tickets, approvals and acceptance in the owning review record; preview affected ticket-blocker changes and obtain confirmation before writing. Keep upstream pending decisions in the conversation and report other execution blockers in the handoff, not a new ledger. Renew affected unit checks/reviews with original roles and re-establish readiness before delivery. Return design decisions to their canonical owners under IMPLEMENTATION.md; originating findings link referrals and approved resolutions, not duplicate design discussions. Synchronize current models/root source and coverage indices only after applicable package approval and confirmation of the exact document changes. Child exceptions cannot override global architecture. Preserve unrelated work and valid evidence with an explicit impact basis.

## Final verification and route-specific review

**Direct change:** implement-unit supplies final combined checks, all approved macro flows, complete target conformance, and a current full-change Pass from the original independent unit reviewer under IMPLEMENTATION.md. That Pass is the final independent assessment; do not dispatch a second overall reviewer, demand a ticket index, or repeat unchanged work for a duplicate review. The controller checks completeness, stable code/source identity, and evidence applicability, not conformance instead of the reviewer. If obligations or evidence are missing or stale, return to the original pair for repair and renewed full-change review. Human acceptance remains the final gate.

**Ticket set:** apply the rest of this section to actual ticket sets only. After all outputs are present, check the root authorized scope on combined code against its applicable flat, hierarchical or change package: final file responsibilities, runtime collaboration, contracts/data/callers, state/resources and obsolete-path retirement. Hierarchy includes shared/child requirements, global architecture and complete applicable technical designs. Trace every selected integration flow to its approved owner and actual participants. Child or ticket-local Passes do not establish closure; unresolved future scope outside the authorization is not silently added. This does not authorize repository-wide redesign.

Run the required project regression checks and every selected macro-flow scenario on the final combined state, using the real participants and approved substitution limits. The runtime-evidence rules in IMPLEMENTATION.md apply. A previously executed assigned flow can count only with an explicit demonstration that the relevant code, participants, configuration, and environment remain applicable. Planned tests, isolated mocks, compile success, and individual ticket Passes cannot establish final collaboration. Mandatory unavailable execution blocks overall Pass and human-acceptance handoff.

Create an independent read-only overall reviewer in a context separate from the controller and ticket implementers, using reviewer-prompt.md. It receives the complete approved set/design and combined change, not a concatenation of local Pass summaries. Retain that overall reviewer across repair rounds. Route each demonstrated implementation/integration issue to the original owner implementer(s), citing its stable finding ID and originating overall report. Ticket repair records link that finding and preserve their own decisions/evidence without copying the overall report. Serialize bounded repairs against current code, then obtain renewed affected ticket review and whole-result review. Do not assign a fresh catch-all agent to refactor the feature after the fact. If the original owner cannot resume, apply the documented handoff rules; if no approved owner exists, resolve that upstream.

The controller and overall reviewer apply these ticket-set categories alongside the full shared unit standard:

1. **Authorized and coherent basis:** valid current sources/authorization, physical prerequisites, preserved user work, and identified combined code.
2. **Complete composition:** whole-target coverage, integrated ownership/contracts, and approved retirement of superseded paths.
3. **Ticket closure and continuity:** all ticket Passes remain applicable with no unresolved findings; original roles and necessary handoffs remain accountable.
4. **Current integrated evidence:** mandatory combined regressions/macro flows meet their approved outcomes and real/substituted scope.
5. **Review and acceptance integrity:** full independent assessment under approved criteria, accurate authority/status claims, and shared artifact integrity.

Use [reviewer-prompt.md](reviewer-prompt.md) for the full overall-review package and verdict contract. The controller cannot aggregate ticket verdicts into overall Pass.

## Human handoff

After mandatory current combined verification and the route-appropriate final independent Pass, preserve the overall submission/evidence and verdict in `implementation.review-fix-decisions.log.md` without duplicating direct or unit evidence. Write the one root `.scratch/<work-slug>/delivery.md` under the shared summary contract, obtain confirmation of the exact root `issue.md` navigation patch before linking the summary, surface consequential autonomous repair decisions with record links, and request explicit acceptance of its selected whole scope. Keep acceptance navigation in the summary, not `issue.md`. Direct work uses its original full-change reviewer; ticket sets require the retained overall reviewer. Delegated units and hierarchical children create no separate delivery and have no per-unit human acceptance gate. Standalone scope follows IMPLEMENTATION.md.

Until the human accepts the current result, report `Awaiting acceptance`. Conformance repairs retain original unit roles and, for sets, the overall reviewer; renew affected evidence/review and integrate the summary before renewed acceptance. New requirements/design decisions follow IMPLEMENTATION.md’s upstream route. Persist the actual scoped human decision and reviewed code/source basis in `implementation.review-fix-decisions.log.md` before updating the summary’s acceptance and evidence link; apply shared revision integrity and retention, not log-based authority.

Stop after acceptance or a genuine external blocker once all reachable authorized work is done. No automatic commit, merge, push, tracker closure, or release; execution does not govern post-delivery design.
