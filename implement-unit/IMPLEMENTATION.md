# Unit Implementation: Execution and Conformance Standard

## Purpose and authority

Use this same standard during implementation, repair, and independent code review. The approved technical target is the normative production-design contract, supplied by flat models, a hierarchical requirements/architecture/child-technical package, or an approved change basis. This standard defines execution and conformance, not a competing architecture or reviewer tastes. Apply it from the first change.

Before starting/resuming any author, controller, or reviewer role, read this entire standard and complete WORKFLOW-ARTIFACTS.md from the named skill `workflow-artifacts`. Apply its loading/resource and reference-only rules; use these criteria before investigation, evidence choices, or edits. This document owns single-unit source validity, code/test/runtime criteria, and original-pair lifecycle. [SKILL.md](SKILL.md) owns the ordered unit workflow; ORCHESTRATION.md owned by named skill `implement` owns whole-work scheduling, combined verification, and route-specific final handoff. Standalone units need no controller; delegated units return to the supplied controller, without recursively loading or executing it. Reviewer prompts may wait until first dispatch, not these execution criteria.

## Approved basis and route validation

A unit has exactly one source route:

- **Ticket:** an authorized ticket from a reviewed, human-approved root set, its index baseline/dependency/coverage entries, and precise authoritative sources. Its baseline may be flat approved requirements and technical models, the hierarchical package below, or the approved change basis. The ticket preserves that target; it makes no new design decisions.
- **Direct change:** the entire reviewed, human-approved CHANGE-MODEL and its exact essential references, including synchronized affected sections of any existing canonical models. Use the change document path and revision as the unit identity. No synthetic ticket, ticket number, ticket-set index, or ticket-set approval is required; the root `issue.md` work entry is still mandatory.

An **approved hierarchical basis** follows WORKFLOW-ARTIFACTS.md’s **Hierarchical source packages and handoffs**: resolve the effort root from supplied root/child entries, then validate its selected scope, exact source revisions and applicable review/approval evidence for shared/child requirements, overall architecture and complete child technical designs. Read precise applicable sections and cross-child prerequisites, not the whole archive. Shared realization, file ownership and contracts must be settled in their owning models before ticketing; architecture or local model Passes alone do not establish a complete consistent implementation basis.

An **approved change basis** supplies changed requirements and a complete scoped technical target with the same rigor as a technical model. It distinguishes observed code/runtime facts, human-confirmed requirements, and unknowns; legacy behavior is not automatically approved. Verify bounded scope, target owners, structure, definitions/contracts, dependencies/prerequisites, acceptance, local/macro verification, and the evidenced execution route. Account for Changed/Unchanged/Unresolved macro topology/data/concurrency/sequences, micro topology/sequences, file organization, and data/contracts. Unchanged claims need precise readable references or evidenced scoped reconstruction; needed unresolved decisions block execution.

The change model and affected canonical model updates must have independent model review and human approval together for the current revisions. Absent old separate requirements/technical models or historical approvals are not missing required inputs when this basis is sufficient. Do not invent retrospective approvals, accept known legacy bugs as requirements, or silently reconstruct missing target decisions during execution. Read the essential references needed to establish affected behavior; a source conflict requires upstream resolution.

**Bounded direct fit:** the approved direct route must show that one implementer/reviewer pair can implement and assess the entire target in one bounded execution cycle, with actual prerequisites available, all affected owners/callers and cutovers identified, and all acceptance, local, macro-flow, and final-conformance obligations executable in that cycle. No unowned remainder or imagined later ticket may carry obligations. Multiple behavior increments and ordinary repair rounds remain one cycle. If evidence instead requires separately scheduled dependent units or scope grows beyond this bound, stop affected execution and return to clarify-change for a renewed reviewed/human-approved route, then split-tickets for approved decomposition. Do not silently narrow the change, fabricate tickets, or force it through the direct route.

For either route establish user implementation authorization, identifiable source revisions and applicable independent-review/human-approval evidence, repository rules, current code basis, and actual prerequisite outputs. Planning approval alone does not authorize execution. Dirty worktrees are allowed: distinguish unit changes from pre-existing user work and retain a reviewable basis without committing, resetting, or removing unrelated changes. Missing required current evidence or an unusable prerequisite is an exact blocker; an absent document not required by the selected route is not.

## Private workspace and records

Reuse the resolved effort root’s `issue.md` as definition/navigation (and set index only on the ticket route), not execution status or an approval-record index. Hierarchical child entries define scoped models: no child ticket pool, controller, state artifact or delivery. A ticket carries one compact non-normative execution block and uses root `issues/NN-<slug>.review-fix-decisions.log.md`; standalone ticket execution creates no artificial overall-controller artifacts. Direct execution uses one `implementation.review-fix-decisions.log.md`, distinct from `change.review-fix-decisions.log.md` for its approved model. The full-scope pair and any controller share one assigned implementation review-log writer, not duplicate direct-unit records. The standalone author/controller establishes the shared exclusion gate before writes; delegated workers use the verified workspace and report problems. Assign one writer per ticket or review log; reviewers remain read-only. Create no standalone state files, substitute progress/checklist files or recovery snapshots.

The existing ticket’s execution block holds only current status, current blocker if any, original implementer/reviewer handles and applicable review/evidence references. Update fields in place, without duplicating planned tasks or chronological progress. Exclude this non-normative block from ticket-specification review revisions under the shared convention; metadata changes cannot amend scope or obligations. The assigned writer preserves an identified review submission with implementation basis, original requirement evidence and actual verification before review; an initial clean result needs no findings or development diary. Later repair decisions/evidence cite existing finding IDs. Save every full reviewer report before repair or advancement, and dispositions plus ticket status when applicable before handoff or dependent scheduling. Apply WORKFLOW-ARTIFACTS.md’s four-event review contract, finding lifecycle, revision/approval integrity, resumption and legacy cutover. Keep design authority in clean models. Resolve source approval through scoped model metadata/logs and ticket-set approval through `tickets.review-fix-decisions.log.md`, not through entry-file approval navigation.

## Persistent roles and invocation modes

Bind each unit to its original implementer and one independent read-only reviewer. Create separate contexts on first assignment; reuse those exact contexts through implementation, repair, re-review, and later conformance repairs during the same implementation effort. Independence means isolation from the implementer, not a new reviewer every round. Different tickets normally get different pairs; a direct change gets one pair for its entire scope. In standalone mode the current author is the implementer and dispatches its bound reviewer; in delegated mode the controller routes both roles using the ticket’s execution metadata, or the direct implementation review log’s compact identity header, and the harness’s resumable context. No copied global role/status ledger, competing reviewers or self-review.

The first review receives the full necessary evidence package. Later rounds send current code identity, changes since the last basis, finding dispositions, new verification, and changed authoritative references. Keep unchanged sources accessible; neither retransmit every document nor supply private author reasoning as reviewer instructions. Both roles assess current code where needed, not stale memory. Re-review covers complete current unit conformance and affected interactions, not only resolved finding IDs; it need not mechanically reread unchanged material.

Initial implementer and replacement packages include the shared dispatch identity/access package, explicit standalone/delegated role and return route, assigned ticket when one exists, review-record paths and each writer, bound roles, exact approved unit/source with scoped approval evidence from model metadata and owning logs, repository rules, current code/user-work boundary, physical prerequisites, and full verification responsibilities. Direct packages use the approved change, actual code and implementation reviews, not a fake ticket or state record. Supply complete applicable standards and readable approved sources to the **author before choices or edits**; giving them only to the reviewer is invalid. Delegated authors receive this skill’s resolved SKILL.md with execution authorization. Initial/replacement reviewers receive [reviewer-prompt.md](reviewer-prompt.md)’s full package and read-only assignment.

After `Changes required`, the original implementer repairs demonstrated violations and renews checks; the original reviewer reassesses the current result. Continue automatically until `Pass` has no unresolved issue. Obtain accessible missing evidence without human intervention. A genuine upstream decision, unavailable capability, or irreducible conflict is a blocker to route to the controller or user, not an ordinary stopping point after one review. No iteration count grants success. If progress stalls, identify the disputed obligation, current evidence, and actual missing decision instead of silently looping or changing reviewers to escape a finding.

Keep original handles in the existing ticket’s execution metadata; when no ticket exists, the existing implementation review log may hold a compact identity header containing only work scope and bound roles. It is ownership metadata, not a fifth event type or a place for progress, blockers or next actions. Completion/handoff references preserve access to the original roles through the harness’s resumable context. Apply shared resumption rules and first attempt to resume the original role. Replace it only when unavailable or demonstrably unable to continue reliably—not for findings, round count or convenience. Transfer the full current initial package, loss reason and handoff basis, intervening changes, implemented result, unresolved findings/blockers, prior dispositions and applicable evidence. Record an authorized replacement and its basis with the affected review submission, and update the current binding in ticket metadata or the identity header; create no role registry or recovery artifact. A replacement reviewer assesses conformance afresh without private author reasoning or inherited Pass; a replacement implementer preserves current code and unrelated user/later-ticket changes.

Before a resumed implementer edits, reconcile its retained understanding with the current shared code and later-ticket/user changes. Preserve those changes and renew affected evidence. A retained reviewer must similarly verify the current snapshot before reusing prior conclusions. Keep roles available for overall-review repairs where the harness permits; genuine later unavailability uses the same explicit handoff procedure.

Delegated authorization covers the assigned unit and ordinary repairs. Review requests are intermediate; only current Pass returns the unit without per-unit human acceptance. Standalone use requires explicit human acceptance of the reviewed scope. Neither a unit Pass nor planning approval establishes whole-set completion or human acceptance; the final route-specific coordination belongs to ORCHESTRATION.md.

## First-pass conformance and decision boundary

Implement directly in the approved file organization, object collaboration, state ownership, data definitions, interfaces, algorithms, concurrency model, and cutover. Preserve the target rationale and concrete quality constraints, including reuse, invariant locality, error/resource ownership, and removal of superseded paths. Several tests or increments may modify the same object; neither a test nor an execution unit justifies splitting it into more production files.

Local names, control-flow expression, and non-semantic simplifications remain engineering choices only where the sources do not prescribe them and they preserve the approved responsibilities, interactions, observable behavior, and quantitative constraints. Do not reserve known design violations or obvious defects for a later cleanup pass. There is no planned rough-code or speculative-refactoring phase. Necessary corrections are still required; first-pass quality is a goal, not permission to hide a discovered defect.

Adding or moving a production responsibility, object, file, design-bearing operation, representation, coordination mechanism, or compatibility path needs an already-approved basis. Return conflicts to the actual decision owner: business rules to `clarify-requirements`, global hierarchical guarantees to `clarify-architecture`, local/shared realization to `clarify-technical-design`, and decomposition to `split-tickets`. Approved-model changes and change-basis conflicts use `clarify-change`’s coordinated scoped package gate, including post-delivery design questions; do not force the whole initial pipeline. Load named routes only for authorized execution. A child addendum cannot override a parent. Renew affected review/human approval, synchronize canonical sources/root indices and dependent tickets, and invalidate affected unit/combined evidence before resuming; preserve unaffected work with an explicit impact basis. Direct expansion follows the bounded-fit gate. Execution authorization is not design-change approval; implementation violations remain original-pair repairs.

Before introducing a new production concept, investigate existing equivalents and their actual roles/contracts. Follow the approved reuse, canonical ownership, locality, and cutover decision. If the model missed an equivalent or prescribed incompatible duplication, return that evidence upstream rather than inventing either a duplicate or different integration. Do not follow a demonstrably defective design blindly or silently replace it. Pending upstream decisions remain explicit beside their affected canonical rules under their owning modeling gate; settled design, original evidence and rationale integrate there, with reviews and approval in that object’s review record. Reflect the blocking dependency in existing ticket metadata when applicable and report it in the handoff for direct work. An originating implementation finding records only its conflict/referral and approved-resolution link, not the upstream discussion.

Each increment must honor the constraints of its approved intermediate state. A local operation may be complete before later public integration; it must not be a stub, fake result, or unauthorized transition. Update all affected callers needed by this unit. Remove code made obsolete by its approved cutover, preserving work explicitly assigned to later tickets and unrelated user changes. A direct change may use intermediate increments but must complete the entire target before Pass.

## Tests that earn their maintenance cost

Inspect the project's test guidance, runner, representative nearby tests, fixtures, and execution environment first. Reuse those means and their established locations. Test behavior through the approved interface at a scope that can detect the target fault. An interface may be a module/object operation, not only a public HTTP endpoint. Test-side files and fixture details follow repository conventions; they do not reopen production design.

For each proposed permanent test, identify the plausible consumer-visible error it detects, the independent expected outcome from the approved contract, and why existing coverage is insufficient. Prefer a small set covering distinct behavior, consequential boundaries, invariants, state transitions, or specified errors. Do not impose method quotas, exhaustive matrices, arbitrary coverage targets, or permanent tests for every mechanical edit. Extend or reuse existing coverage where it already provides the needed evidence.

Assertions must observe the promised result, permitted state, or externally meaningful effect. Avoid assertions on private structure, arbitrary call counts, source text, copied constants, mock echoes, or test expectations computed by repeating the implementation. Assert ordering or interactions only where the contract actually makes them observable obligations. Do not retain implementation-coupled or tautological tests merely by updating their expected incidental details; remove them and use behavior coverage where needed.

Use real owned collaboration where that collaboration is the subject of the test. A substitute at a justified external dependency can isolate behavior, but declare what it replaces and what the result cannot prove. A mocked store does not prove persistence or cross-process atomicity. Follow the approved production interfaces; do not add an abstraction, change ownership, or introduce a production dependency solely to make a test easier to mock. If the required behavior cannot be exercised with the available means, establish the gap and route a necessary production-design change upstream.

## TDD within the approved design

For new or changed behavior without adequate coverage:

1. Select one meaningful behavior from the approved contract and add the smallest useful test using existing facilities.
2. Run it before implementing the behavior. Observe a failure attributable to the missing or incorrect behavior. Resolve broken fixtures, unavailable services, or unrelated compilation errors separately. A missing new declaration may explain an initial compile failure, but compilation failure alone is not the behavioral assertion's red evidence: establish the test's sensitivity once the interface can be exercised without treating setup scaffolding as a completed increment.
3. Implement only the selected behavior, directly in its approved owners and collaboration. Minimal means no speculative features, not bypassing the design, hard-coding the observed example, or weakening the contract to pass.
4. Run the test and relevant nearby checks; confirm the specified outcome. Continue with the next justified behavior, incorporating evidence from the actual result rather than writing all imagined tests first.

When an existing test already demonstrates the failure, reuse its red/green result instead of duplicating it. For behavior-preserving work, run meaningful existing regression coverage before and after and exercise the affected path; do not manufacture a failing test to prove an unchanged requirement. If the user already supplies a failure, use that observed evidence rather than rerunning only to reconfirm it. If no reliable automated test is feasible, record the concrete limitation and run an appropriate direct scenario; never call that a completed automated TDD cycle. A mandatory test or flow remains mandatory and cannot be waived by this fallback.

Ordinary edits or corrections may improve local expression while preserving the settled design, but there is no separate planned refactor stage. A green check is necessary evidence for its assertions, not permission to leave a known structural violation, declare unrelated behavior correct, or defer design compliance until review.

## Runtime and regression evidence

Use project-provided commands and select checks for the actual changed behavior, contracts, and callers. Run applicable static checks and meaningful targeted/regression tests. At completed-unit handoff, run the normal project suite required by its guidance; inaccessible mandatory portions are blockers, not permission for a narrow passing substitute. Do not change unrelated failing code or suppress failures to manufacture a pass. Distinguish established pre-existing failures from change-caused failures, with evidence and affected confidence.

Exercise the actual changed runtime surface, not just compilation or isolated mocked tests. A CLI change needs a real invocation and observed output/state; a UI change needs interaction with the actual UI; a library operation needs a direct caller scenario or integration harness. Existing real-flow tests may supply this runtime evidence when they genuinely exercise the changed surface with observable results; do not duplicate identical execution just to produce another artifact. A disposable caller probe can fill a gap without becoming a permanent low-value test. Record the visual or environment limit if an actual surface is unavailable; a mandatory unverified result prevents Pass.

Implement and execute every macro-flow test assigned to this unit, with its prescribed real participants and substitution limits, including applicable cross-child interactions. A ticket may leave only an explicitly identified later-owned flow outside its local usable-increment claim. An assigned flow lacking participants/setup blocks Pass. A direct unit owns all change flows and final coverage: demonstrate that owners, contracts, callers, state/resources, and cutovers compose on final combined code, with mandated regression/macro results. ORCHESTRATION.md governs final handoff against the root selected scope; child or ticket Passes cannot establish whole delivery.

Persist code-bound verification in the owning review log as review-submission evidence or finding-linked repair evidence under the shared contract, not a chronological test diary. After repairs renew affected checks; reuse earlier evidence only with explicit unchanged relevant code/environment applicability. Preserve historical outcomes while marking invalidation.

## Independent conformance review

Review assesses the implemented result against the same sources used to implement it, not a second design exercise. Every blocking finding identifies a governing approved technical or requirements obligation, applicable repository rule, unit acceptance condition, or execution/verification rule here, with code/evidence location and concrete consequence. A preferred pattern, shorter method, naming style, or alternative architecture without a demonstrated violation is not a required correction.

Classify findings by ownership:

- **Implementation violation:** the approved basis is usable but code, tests, integration, or evidence does not satisfy it. Correct the implementation and renew verification.
- **Upstream defect:** the approved requirements/technical target or ticket is contradictory, incomplete, or demonstrably unable to satisfy the requirement. Return evidence through the design-boundary route; do not approve incorrect behavior or let the reviewer invent a replacement design.
- **Unavailable evidence:** conformance cannot yet be assessed. Identify the missing input or check and how to unblock it; do not speculate that unseen code is defective.

Read the complete current unit change and sufficient surrounding implementations/callers to evaluate all affected obligations. A diff alone or only prior failing lines is insufficient. Keep scope bounded to the change and necessary interactions, not a repository-wide architecture audit. Reuse the bound independent reviewer for every repair round under the persistent-role rules; review complete current conformance and regressions outside original findings using retained unchanged context and refreshed evidence. A role switch or author self-review is not independent review.

Use reviewer-prompt.md for the evidence package and report. Report these categories against the full standard:

1. **Approved and executable basis:** the complete route-validation criteria, current authorization and approvals, repository rules, code identity, and usable prerequisites.
2. **Structural conformance:** first-pass organization, ownership, reuse/locality, collaboration, and cutover criteria.
3. **Behavioral conformance:** approved definitions/contracts, algorithms, resource/error behavior, concurrency, and requirement outcomes.
4. **Test value and execution:** the test-value and TDD criteria, including justified alternatives and substitution limits.
5. **Runtime and integration evidence:** the complete runtime/regression criteria and ticket-local versus full-change evidence scope.
6. **Complete and reviewable handoff:** current callers/tests/documentation, no in-scope obsolete paths or scaffolding, identifiable code/evidence, no unresolved findings/blockers, and WORKFLOW-ARTIFACTS.md integrity.

These categories index the standard and do not authorize new design rules. `Changes required` means a demonstrated violation, including an upstream defect that prevents conforming delivery; report any additional blockers. `Blocked` means missing evidence or access prevents assessment without a demonstrated violation. `Pass` requires every applicable category satisfied, no unresolved finding or blocker, and mandatory current evidence. A personal preference cannot prevent Pass.

## Delivery and clean artifacts

Deliver conforming code and necessary tests/documentation with actual evidence and independent assessment of the same result. Update affected existing documentation in place without using it to authorize redesign. Remove disposable probes after preserving useful observations. Canonical sources remain clean under the shared contract.

After required verification/current Pass, the assigned writer persists the verdict and updates the existing ticket’s execution status where applicable before handoff. Delegated units return scope/evidence, consequential autonomous repair decisions and ticket/review-record references to their controller, which owns whole-work delivery under ORCHESTRATION.md. Direct work returns its approved change and implementation review references, not a substitute status artifact. Before standalone human acceptance, the author writes `.scratch/<work-slug>/delivery.md` using the shared summary contract and surfaces significant autonomous repair decisions with their records; a standalone ticket identifies only its reviewed scope and preserves any broader existing summary.

Use the shared revision/acceptance rules for repairs and decisions: renew affected evidence and complete current-scope review with the original reviewer before renewed handoff. Ticket execution status distinguishes unfinished/blocked work from independently passed work; applicable review evidence establishes direct conformance, and the delivery summary distinguishes awaiting acceptance from explicitly accepted scope. Persist the actual scoped human decision and reviewed code/source basis in the owning review log before updating the summary’s acceptance and evidence link. Keep `issue.md` limited to specification navigation, without approval-record links. Retain excluded artifacts under the shared contract.

Stop at the authorized unit handoff; do not execute another unit or automatically commit, merge, push, close tracker issues, or release. Post-delivery design questions follow the design-boundary route, not an implementation-role redesign.
