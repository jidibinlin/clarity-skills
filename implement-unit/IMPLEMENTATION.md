# Unit Implementation: Execution and Conformance Standard

## Purpose and authority

Use this same standard during implementation, repair, and independent code review. The approved technical target is the normative production-design contract, whether supplied by a technical model or an approved change basis. This standard defines execution and conformance, not a competing architecture or reviewer tastes. Apply it from the first change.

Before authoring, resumption, or review, load `workflow-artifacts` by registered name using the Skill tool or the harness's equivalent named mechanism (omp: `skill://workflow-artifacts`) and read its WORKFLOW-ARTIFACTS.md from that skill's resolved installed location. Its private-storage, pre-write exclusion, clean-authority, record, revision, and recovery contract is mandatory. Reuse a supplied complete current standard or verified readable resource with its owning skill identity without recursively loading it; a summary is not sufficient. Missing or inaccessible required standards block affected work; report the exact dependency, without guessing sibling paths or auto-installing.

This resource and [reviewer-prompt.md](reviewer-prompt.md) belong to `implement-unit`; companion links resolve from that installed skill/document under [SKILL.md](SKILL.md), not the target checkout. Consulting this standard is reference-only and starts no implementation, artifacts, or reviewer pair. Product code, commands, and `.scratch/` use the identified target repository. Standalone use does not require `implement`; delegated execution returns to its existing controller, not a recursively loaded controller. Upstream stage routes name `clarify-requirements`, `clarify-technical-design`, `clarify-change`, and `split-tickets`: load their required references by name in reference-only mode, or execute a stage only when authorized under its existing gates.

## Approved basis and route validation

A unit has exactly one source route:

- **Ticket:** an authorized ticket from a reviewed, human-approved set, its index baseline and dependency/coverage entries, and exact authoritative requirements/technical references. Its baseline may be approved requirements and technical models, or the approved change basis below. The ticket preserves that target; it does not make new design decisions.
- **Direct change:** the entire reviewed, human-approved CHANGE-MODEL and its exact essential references, including synchronized affected sections of any existing canonical models. Use the change document path and revision as the unit identity. No synthetic ticket, ticket number, ticket-set index, or ticket-set approval is required; the root `issue.md` work entry is still mandatory.

An **approved change basis** supplies changed requirements and a complete scoped technical target with the same rigor as a technical model. It distinguishes observed current code/runtime facts, human-confirmed requirements, and unknowns; legacy behavior is not automatically an approved requirement. Verify bounded scope, precise target owners, structure, definitions and contracts, dependencies/prerequisites, acceptance conditions, local and macro verification, and an evidence-backed direct-versus-decomposed route. It explicitly accounts for Changed, Unchanged, or Unresolved macro topology/data/concurrency/sequences, micro topology/sequences, file organization, and data/contracts. Unchanged claims need readable precise references or reconstructed scoped evidence and a confirmed target, not an absent historical document. Unresolved matters affecting executable obligations block that work; irrelevant unknowns must be explicitly outside scope.

The change model and affected canonical model updates must have independent model review and human approval together for the current revisions. Absent old separate requirements/technical models or historical approvals are not missing required inputs when this basis is sufficient. Do not invent retrospective approvals, accept known legacy bugs as requirements, or silently reconstruct missing target decisions during execution. Read the essential references needed to establish affected behavior; a source conflict requires upstream resolution.

**Bounded direct fit:** the approved direct route must show that one implementer/reviewer pair can implement and assess the entire target in one bounded execution cycle, with actual prerequisites available, all affected owners/callers and cutovers identified, and all acceptance, local, macro-flow, and final-conformance obligations executable in that cycle. No unowned remainder or imagined later ticket may carry obligations. Multiple behavior increments and ordinary repair rounds remain one cycle. If evidence instead requires separately scheduled dependent units or scope grows beyond this bound, stop affected execution and return to clarify-change for a renewed reviewed/human-approved route, then split-tickets for approved decomposition. Do not silently narrow the change, fabricate tickets, or force it through the direct route.

For either route establish user implementation authorization, identifiable source revisions and applicable independent-review/human-approval evidence, repository rules, current code basis, and actual prerequisite outputs. Planning approval alone does not authorize execution. Dirty worktrees are allowed: distinguish unit changes from pre-existing user work and retain a reviewable basis without committing, resetting, or removing unrelated changes. Missing required current evidence or an unusable prerequisite is an exact blocker; an absent document not required by the selected route is not.

## Private workspace and records

Reuse `.scratch/<work-slug>/issue.md` as the work entry/recovery map; on the ticket route it also owns the set index. A ticket lives at `issues/NN-<slug>.md` and records implementation, reviews, repairs, evidence and handoffs in its same-stem `.log.md`. Direct execution uses root `issue.log.md`, with no fake ticket or `issues/` directory. Existing authoritative project models may remain precisely referenced at their established locations; integrate approved revisions into their owning sections, never into log-based overrides.

Before artifact writes, the standalone author or controller establishes/verifies local Git exclusion under WORKFLOW-ARTIFACTS.md: actual root and worktree-aware exclusion path, preserved rules, blocking any tracked workflow paths, and effective ignore evidence. Delegated workers consume the verified workspace and report failures; they do not race exclusion edits. The controller alone writes shared `issue.md` and `issue.log.md`. Delegated implementers supply entries or write only an exclusively assigned ticket log. The standalone author owns recording; reviewers are always read-only.

At each meaningful implemented result or repair batch, record objective/acceptance or stable finding IDs, actual resulting behavior and owners, handling decision and key rationale, whether it remains within approved design, precise fresh verification and limits, open issues and next action. No per-tool diary or private reasoning dump is required. Clean implementations still need result/evidence records.

Before requesting review, persist those decisions and fresh evidence. Before dispatching repair or advancing any gate, persist the returned review with stage/unit, round, date, reviewer identity, exact source/code basis, governing standards, actual verdict, category coverage, findings/blockers and prior dispositions. Save failed and blocked reviews too. Stable IDs follow findings across rounds; authors can report addressed/awaiting review but only the applicable reviewer confirms correction or withdrawal. Disputes stay open with counter-evidence. Persist dispositions and current state before scheduling dependents or handoff; update the recovery entry before blockers, role replacement, or session/stage transitions.

Identify private sources with path plus digest or another verifiable local revision mechanism, covering every relevant package member and distinguishing metadata-only changes consistently. Repository HEAD alone cannot identify ignored sources. Identify code by checkout and relevant dirty/new file content as well as any commit. Preserve essential observed evidence and decisions locally, not only transient agent/tool links. Logs are neither Git history nor complete snapshots; do not invent unavailable historical bodies or retain unverifiable approvals.

## Persistent roles and invocation modes

Bind each unit to its original implementer and one independent read-only reviewer. Create separate contexts on first assignment; reuse those exact contexts through implementation, repair, re-review, and later conformance repairs during the same implementation effort. Independence means isolation from the implementer, not a new reviewer every round. Different tickets normally get different pairs; a direct change gets one pair for its entire scope. In standalone mode the current author is the implementer and dispatches its bound reviewer; in delegated mode the controller owns both handles and routes requests, reports, and repairs. Do not create competing reviewers or self-review.

The first review receives the full necessary evidence package. Later rounds send current code identity, changes since the last basis, finding dispositions, new verification, and changed authoritative references. Keep unchanged sources accessible; neither retransmit every document nor supply private author reasoning as reviewer instructions. Both roles assess current code where needed, not stale memory. Re-review covers complete current unit conformance and affected interactions, not only resolved finding IDs; it need not mechanically reread unchanged material.

Initial and replacement packages identify the target repository/checkout and work identity, owning skills `implement-unit` and `workflow-artifacts`, and complete current required standards/reviewer instructions or verified resolved installed resources. Delegated implementation receives the resolved installed SKILL.md with an explicit unit execution assignment; reviewer skill loads remain reference-only with an independent read-only assignment. Reuse intact supplied standards instead of recursively loading skills or duplicating a controller/reviewer.

After `Changes required`, the original implementer repairs demonstrated violations and renews checks; the original reviewer reassesses the current result. Continue automatically until `Pass` has no unresolved issue. Obtain accessible missing evidence without human intervention. A genuine upstream decision, unavailable capability, or irreducible conflict is a blocker to route to the controller or user, not an ordinary stopping point after one review. No iteration count grants success. If progress stalls, identify the disputed obligation, current evidence, and actual missing decision instead of silently looping or changing reviewers to escape a finding.

Retain role handles and compact current recovery state in `issue.md`, with evidence and open findings linked to the owning log. On resumption read that entry, relevant current sources/ticket, open findings, latest applicable evidence/decisions, and older entries only as needed. First attempt to resume the original role after interruption. Replace it only when its session is unavailable or demonstrably cannot reliably continue; findings, round count, and convenience are not reasons. Before replacement persist the reason and transfer unit/source identities, current code basis and intervening changes, scope/prerequisites, implemented result, unresolved findings/blockers, prior dispositions, and applicable test/runtime evidence. A replacement reviewer receives the full package without private implementer reasoning and establishes conformance rather than inheriting Pass. A replacement implementer receives current work and unresolved obligations, not permission to overwrite later changes. Record the new handle and handoff basis before continuation.

Before a resumed implementer edits, reconcile its retained understanding with the current shared code and later-ticket/user changes. Preserve those changes and renew affected evidence. A retained reviewer must similarly verify the current snapshot before reusing prior conclusions. Keep roles available for overall-review repairs where the harness permits; genuine later unavailability uses the same explicit handoff procedure.

In delegated mode the controller's execution authorization covers the assigned unit and ordinary conformance repairs. Intermediate review requests are not completion. A current independent Pass returns the unit without per-unit human acceptance; the controller owns continuation and final whole-result human review. In standalone mode present the reviewed unit and request explicit acceptance before calling it human-approved. A direct unit's Pass covers the entire change and final combined runtime evidence: it is the final independent review, not an input to a duplicate overall review. Ticket-local Passes do not prove composition. No Pass or planning approval implies human acceptance.

## First-pass conformance and decision boundary

Implement directly in the approved file organization, object collaboration, state ownership, data definitions, interfaces, algorithms, concurrency model, and cutover. Preserve the target rationale and concrete quality constraints, including reuse, invariant locality, error/resource ownership, and removal of superseded paths. Several tests or increments may modify the same object; neither a test nor an execution unit justifies splitting it into more production files.

Local names, control-flow expression, and non-semantic simplifications remain engineering choices only where the sources do not prescribe them and they preserve the approved responsibilities, interactions, observable behavior, and quantitative constraints. Do not reserve known design violations or obvious defects for a later cleanup pass. There is no planned rough-code or speculative-refactoring phase. Necessary corrections are still required; first-pass quality is a goal, not permission to hide a discovered defect.

Adding or moving a production responsibility, object, file, design-bearing operation, representation, coordination mechanism, or compatibility path needs an already-approved basis. Change-basis requirement, domain, design, and source conflicts return with evidence to clarify-change, including post-delivery design questions; do not force a rerun of the original two-stage pipeline. For an original requirements/technical-model baseline, return missing business behavior to requirements clarification, missing production decisions to technical clarification, and decomposition defects to split-tickets. Direct-scope expansion follows the bounded-fit gate above. Renew affected upstream review and human approval and refresh dependent tickets before resuming. Execution roles do not govern design or rewrite models to justify unapproved code.

If inspection reveals an existing equivalent concept, verify its actual role and contract. Use the approved reuse decision; if the model missed it or prescribed an incompatible duplication, return the evidence upstream rather than inventing either a duplicate or a different integration. Do not follow a demonstrably defective design blindly, but do not silently replace it either.

Each increment must honor the constraints of its approved intermediate state. A local operation may be complete before later public integration; it must not be a stub, fake result, or unauthorized transition. Update all affected callers needed by this unit. Remove code made obsolete by its approved cutover, preserving work explicitly assigned to later tickets and unrelated user changes. A direct change may use intermediate increments but must complete the entire target before Pass.

## Tests that earn their maintenance cost

Inspect the project's test guidance, runner, representative nearby tests, fixtures, and execution environment first. Reuse those means and their established locations. Test behavior through the approved interface at a scope that can detect the target fault. An interface may be a module/object operation, not only a public HTTP endpoint. Test-side files and fixture details follow repository conventions; they do not reopen production design.

For each proposed permanent test, identify the plausible consumer-visible error it detects, the independent expected outcome from the approved contract, and why existing coverage is insufficient. Prefer a small set covering distinct behavior, consequential boundaries, invariants, state transitions, or specified errors. Do not impose method quotas, exhaustive matrices, arbitrary coverage targets, or permanent tests for every mechanical edit. Extend or reuse existing coverage where it already provides the needed evidence.

Assertions must observe the promised result, permitted state, or externally meaningful effect. Avoid assertions on private structure, arbitrary call counts, source text, copied constants, mock echoes, or test expectations computed by repeating the implementation. Assert ordering or interactions only where the contract actually makes them observable obligations. Do not retain implementation-coupled or tautological tests merely by updating their expected incidental details; remove them and use behavior coverage where needed.

Use real owned collaboration where that collaboration is the subject of the test. A substitute at a justified external dependency can isolate behavior, but declare what it replaces and what the result cannot prove. A mocked store does not prove persistence or cross-process atomicity. Follow the approved production interfaces; do not add an abstraction, change ownership, or introduce a production dependency solely to make a test easier to mock. If the required behavior cannot be exercised with the available means, establish the gap and route a necessary production-design change upstream.

## TDD within the approved design

For new or changed behavior without adequate coverage:

1. Select one meaningful behavior from the approved contract and add the smallest useful test using existing facilities.
2. Run it before implementing the behavior. Observe a failure attributable to the missing or incorrect behavior. Resolve broken fixtures, unavailable services, or unrelated compilation errors separately. A missing new declaration may explain an initial compile failure, but compilation failure alone is not the behavioral assertion's red evidence: establish the test's sensitivity once the interface can be exercised without treating setup scaffolding as a completed increment.
3. Implement only the selected behavior, directly in its approved owners and collaboration. Minimal means no speculative features, not bypassing the design, hard-coding the observed example, or weakening the contract to pass.
4. Run the test and relevant nearby checks; confirm the specified outcome. Continue with the next justified behavior, incorporating evidence from the actual result rather than writing all imagined tests first.

When an existing test already demonstrates the failure, reuse its red/green result instead of duplicating it. For behavior-preserving work, run meaningful existing regression coverage before and after and exercise the affected path; do not manufacture a failing test to prove an unchanged requirement. If the user already supplies a failure, use that observed evidence rather than rerunning only to reconfirm it. If no reliable automated test is feasible, record the concrete limitation and run an appropriate direct scenario; never call that a completed automated TDD cycle. A mandatory test or flow remains mandatory and cannot be waived by this fallback.

Ordinary edits or corrections may improve local expression while preserving the settled design, but there is no separate planned refactor stage. A green check is necessary evidence for its assertions, not permission to leave a known structural violation, declare unrelated behavior correct, or defer design compliance until review.

## Runtime and regression evidence

Use project-provided commands and select checks for the actual changed behavior, contracts, and callers. Run applicable static checks and meaningful targeted/regression tests. At completed-unit handoff, run the normal project suite required by its guidance; inaccessible mandatory portions are blockers, not permission for a narrow passing substitute. Do not change unrelated failing code or suppress failures to manufacture a pass. Distinguish established pre-existing failures from change-caused failures, with evidence and affected confidence.

Exercise the actual changed runtime surface, not just compilation or isolated mocked tests. A CLI change needs a real invocation and observed output/state; a UI change needs interaction with the actual UI; a library operation needs a direct caller scenario or integration harness. Existing real-flow tests may supply this runtime evidence when they genuinely exercise the changed surface with observable results; do not duplicate identical execution just to produce another artifact. A disposable caller probe can fill a gap without becoming a permanent low-value test. Record the visual or environment limit if an actual surface is unavailable; a mandatory unverified result prevents Pass.

Implement and execute the macro-flow tests assigned to this unit by its approved technical target, with specified real participants and substitution limits. For a ticket, name any specifically assigned later ticket that owns an incomplete flow and limit local claims to the approved usable increment. If this unit owns a flow, missing participants or setup block Pass, not defer execution past release or joint-integration handoff. A direct unit owns all change flows and final coverage: demonstrate that all owners, contracts, callers, state/resource handling, and cutovers compose on the final combined code, with all mandated regression and macro-flow results. Its persistent reviewer assesses that full result once per candidate; no duplicate unit/overall assessment is required. Real ticket sets still require final combined verification and overall review; local Passes alone do not prove composition.

For each verification result, retain the exact command or interaction/scenario, tested code basis, relevant environment/real-versus-substituted scope, expected observation, actual outcome and material output/assertions, and limitations in the owning unit log (root `issue.log.md` for direct work). Distinguish planned, executed, failed, and passed checks; transient harness output alone is insufficient. Do not put an execution diary in canonical models or tickets. Re-run affected checks after a repair. Reuse earlier evidence only when its code and relevant environment remain applicable; identify that basis explicitly and mark invalidated prior results without erasing them.

## Independent conformance review

Review assesses the implemented result against the same sources used to implement it, not a second design exercise. Every blocking finding identifies a governing approved technical or requirements obligation, applicable repository rule, unit acceptance condition, or execution/verification rule here, with code/evidence location and concrete consequence. A preferred pattern, shorter method, naming style, or alternative architecture without a demonstrated violation is not a required correction.

Classify findings by ownership:

- **Implementation violation:** the approved basis is usable but code, tests, integration, or evidence does not satisfy it. Correct the implementation and renew verification.
- **Upstream defect:** the approved requirements/technical target or ticket is contradictory, incomplete, or demonstrably unable to satisfy the requirement. Return evidence through the design-boundary route; do not approve incorrect behavior or let the reviewer invent a replacement design.
- **Unavailable evidence:** conformance cannot yet be assessed. Identify the missing input or check and how to unblock it; do not speculate that unseen code is defective.

Read the complete current unit change and sufficient surrounding implementations/callers to evaluate all affected obligations. A diff alone or only prior failing lines is insufficient. Keep scope bounded to the change and necessary interactions, not a repository-wide architecture audit. Reuse the bound independent reviewer for every repair round under the persistent-role rules; review complete current conformance and regressions outside original findings using retained unchanged context and refreshed evidence. A role switch or author self-review is not independent review.

Use reviewer-prompt.md for the evidence package and report. Report these categories against the full standard:

1. **Approved and executable basis:** current authorized ticket or bounded direct change, consistent route-appropriate approved sources, applicable repository rules, identified code basis, and actual prerequisite outputs.
2. **Structural conformance:** file/object ownership, reuse, state/invariant locality, collaboration, and cutover match the approved design; no unauthorized production concepts or temporary paths.
3. **Behavioral conformance:** definitions, interfaces, algorithms, resource/error handling, concurrency, and relevant requirement outcomes agree with the sources and actual implementation.
4. **Test value and execution:** necessary behavior evidence, honest red/green or justified alternative, independent assertions, maintained regression coverage, and truthful substitution limits.
5. **Runtime and integration evidence:** the changed surface and assigned macro flows ran as required; ticket claims distinguish local increments from complete collaboration, while a direct unit proves the entire final change and its combined runtime behavior.
6. **Complete and reviewable handoff:** affected callers/tests/documentation are current, no in-scope obsolete path or scaffolding remains, code and evidence identify the reviewed result, and no unresolved finding or blocker is hidden. WORKFLOW-ARTIFACTS.md requirements hold for private paths/exclusion, durable records and finding lifecycle, exact source/code revisions, and current recovery state; logs do not redefine approved design.

These categories index the standard and do not authorize new design rules. `Changes required` means a demonstrated violation, including an upstream defect that prevents conforming delivery; report any additional blockers. `Blocked` means missing evidence or access prevents assessment without a demonstrated violation. `Pass` requires every applicable category satisfied, no unresolved finding or blocker, and mandatory current evidence. A personal preference cannot prevent Pass.

## Delivery and clean artifacts

The deliverable is conforming code and necessary tests/documentation, accompanied by concise verification evidence and an independent assessment of the same result. Keep canonical design and ticket documents as clean descriptions, not logs. Do not add patch documents, changelogs, override addenda, embedded review reports, or speculative cleanup lists to them. Update existing documentation affected by the approved implementation in place; do not use documentation edits to authorize a different design. Remove disposable probes you created after preserving their useful observations.

After required verification and current independent Pass, persist the review and state before handoff. Delegated units return their reviewed scope and record links to the controller; they do not create or claim whole-work delivery. Before standalone human acceptance, write `.scratch/<work-slug>/delivery.md` following WORKFLOW-ARTIFACTS.md: delivered scope/exclusions, final design landing with precise authority links, consequential decisions/basis, actual verification/review and limits, applicable use/maintenance guidance, and `Awaiting acceptance`. A standalone ticket summarizes only its explicitly reviewed scope, never the entire set; preserve any existing broader summary. The controller owns whole-work delivery for delegated execution.

Record explicit human acceptance with exact scope/basis and faithful actual decision evidence in the owning log, then update the entry and summary. Renew affected evidence/review and integrate `delivery.md` before requesting acceptance after repair. A summary is not a process log or competing design authority; retain all private excluded records after completion and never automatically publish, commit, move out, or delete them.

Distinguish unfinished/blocked work, an independently passed unit returned to its controller, a standalone or whole-result handoff awaiting human acceptance, and an explicitly accepted result. Planning status `Approved` is not implementation completion; a reviewer never grants human approval. Content changes, relevant upstream changes, or changed integration assumptions invalidate affected review/acceptance; metadata-only changes do not. Renew evidence and full-scope review with the original reviewer, using recovery rules if necessary. Delegated units need no individual human acceptance; acceptance applies at the authorized standalone or whole-result handoff.

Stop at the authorized unit's reviewed return; do not independently execute another unit, commit, merge, push, close tracker issues, or release. The existing `implement` controller continues an authorized ticket set and owns its final combined review and macro-flow execution; return through its supplied handle without loading or executing it again. For a direct change, the unit supplies that complete evidence and its current full-change Pass serves as final independent review; the controller still owns final human acceptance. Post-delivery design questions return to `clarify-change`, loaded by name only for authorized upstream work; this standard executes the approved result rather than governing change design.
