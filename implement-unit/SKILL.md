# Implement Unit

**Entry mode:** When loaded by a controller or reviewer for IMPLEMENTATION.md or reviewer-prompt.md, this skill is reference-only: read the requested resources and mandatory shared contract, then return without implementing, creating artifacts, spawning a pair, or requesting acceptance. Execute the numbered workflow only for authorized standalone work or an explicit delegated unit assignment; dependency loading is not that assignment.

Translate one approved work unit into conforming, verified code. A unit is either one ticket from an approved set or one entire bounded approved change, without a ticket. The approved technical target constrains the first implementation; independent review checks conformance rather than redesigning the solution. TDD supplies behavior evidence, not permission to improvise architecture. Do not plan a rough implementation followed by structural cleanup.

Before starting, resuming, or reviewing, load the registered skill `workflow-artifacts` by name using the Skill tool or the harness's equivalent named resource mechanism (omp: `skill://workflow-artifacts`), and read its WORKFLOW-ARTIFACTS.md. Read [IMPLEMENTATION.md](IMPLEMENTATION.md). The shared contract governs private storage, records, recovery, and resource resolution; IMPLEMENTATION.md governs execution and independent review, including both source routes and their input gates. Read [reviewer-prompt.md](reviewer-prompt.md) when dispatching review. Install this complete skill and its named dependency independently. Delegated execution is coordinated by `implement`, not by a sibling-directory requirement or recursive controller load. No external TDD or code-review skill may replace these gates with different design or approval rules.

Resolve companions from their owning installed skill/document, not the product checkout or another skill. Reuse supplied complete current standards or verified readable resources with their owning skill identities; summaries do not suffice and intact inputs need no recursive load. Missing, ambiguous, or inaccessible dependencies block affected work: report the exact skill/resource and needed access, without guessing locations or auto-installing. Keep the read-only skill installation distinct from the target repository, where code, commands, and `.scratch/<work-slug>/` belong.

Stage routes name `clarify-requirements`, `clarify-technical-design`, `clarify-change`, `split-tickets`, and `implement`. Load a selected stage by name only when its reference is needed or execution is authorized; reference access never starts that stage or bypasses any stop or approval gate. A delegated unit uses its supplied controller contract and return handle; do not load or execute `implement` again, create another controller, or duplicate its reviewer.

Establish standalone or delegated mode. In delegated mode, the implement controller binds this unit to one persistent implementer and one independent persistent reviewer. Apply IMPLEMENTATION.md's role-lifecycle rules. Return intermediate review requests and blockers to that controller; return a successful unit result only after the review loop passes. Do not request per-unit human approval or spawn a second reviewer when the controller supplies one. In standalone mode the current author is the implementer and manages the same persistent review loop before the user-facing handoff.

## 1. Establish the executable work unit

Identify the source route and apply IMPLEMENTATION.md's approved-basis and bounded-direct-fit gates. For a ticket, read the selected ticket, index baseline, dependencies, and exact authoritative requirements/technical references. For a direct change, read the reviewed and human-approved CHANGE-MODEL, exact essential references, and synchronized affected canonical model sections; its path and revision identify the unit. Do not require or fabricate a ticket, ticket-set index, old separate models, or historical approvals. Establish the applicable independent reviews, current human approvals, and the user's implementation authorization; upstream approval alone does not auto-start work. Do not reopen settled choices or ask for repository facts.

Inspect the actual affected code, callers, repository rules, test facilities, and existing workspace changes. Identify the current code basis without requiring a clean worktree, committing user changes, or treating a status label as evidence. Confirm prerequisite outputs exist and work as required. A ticket number, predecessor completion claim, or approved plan cannot substitute for its usable output.

Use the existing `.scratch/<work-slug>/issue.md` work entry for both routes; on the ticket route it also serves as set index. Direct work creates no ticket or ticket-set index. Before artifact writes the standalone author establishes/verifies WORKFLOW-ARTIFACTS.md's local Git exclusion, including worktree-aware paths, tracked-file blocking, and effective ignore evidence. Delegated workers use the controller's verified workspace and report problems without racing exclusion edits. Recover from the entry, relevant current sources/ticket, open findings, latest decisions/evidence, and original role handles—not conversation memory.

Apply the standard's design-boundary rules. Missing production decisions, stale evidence, contradictions, or unmet prerequisites block affected work. Change-basis conflicts and post-delivery design questions return with concrete source/code evidence to clarify-change, not a forced rerun of the original requirements/technical pipeline. If a direct change no longer fits one bounded execution cycle, stop affected work and return for reviewed, human-approved decomposition; do not squeeze it into one unit or invent tickets. Resume only on the renewed approved basis.

## 2. Choose evidence for this unit's behavior

Using the actual project's runner, representative tests, fixtures, and local/CI commands, identify the behavior and invariants this unit must demonstrate. Reuse existing coverage and approved interfaces; specify which real interactions a proposed check exercises and which it substitutes. Apply IMPLEMENTATION.md's test-value and TDD rules rather than prescribing one test per method or an exhaustive matrix.

Do not ask the human to reconfirm approved contracts or ordinary test details. Escalate only a consequential unresolved choice that changes product behavior, production structure, or an authorized verification constraint. Testing inconvenience is not permission to create production abstractions. Locate the assigned macro-flow responsibilities and establish whether their real participants are available. A direct unit owns every flow and final-conformance obligation of the approved change; it has no later ticket to absorb them.

## 3. Implement each behavior in the approved structure

For each uncovered behavior, execute one meaningful failing test, establish why it fails, implement that behavior directly in its approved owners, and rerun the check. Continue with the next justified behavior. Existing adequate tests may provide evidence without redundant additions; behavior-preserving work uses the applicable path in IMPLEMENTATION.md. Investigate environment or fixture failures rather than calling them behavioral red evidence.

Minimal implementation means no speculative work, not a temporary violation of the technical design. Keep state, invariants, error/resource handling, collaboration, and cutover conforming from the first increment. Make ordinary local expression choices within those constraints; do not introduce a file, object, protocol, or compatibility layer to get a quick green result. Correct observed defects where they arise, not in a planned later refactoring phase.

Preserve unrelated user work. Update affected callers, tests, and existing documentation within the unit's approved scope. If a change needs an upstream design decision, stop that path and return evidence rather than writing a substitute design. Keep canonical models, change models, and tickets clean; do not append patches, logs, override notes, or review reports.

Persist meaningful implementation/repair results in the same-stem `issues/NN-<slug>.log.md`, or root `issue.log.md` for direct work. Include objective/finding IDs, resulting behavior and owners, handling decision and necessary rationale, approved-design boundary, actual code-bound evidence, remaining issues, and next action. In delegated mode supply entries to the controller unless assigned exclusive unit-log ownership; never write the shared entry/root log concurrently. Clean implementation needs a record even without findings.

## 4. Exercise the completed increment

Run the project's applicable static checks and behavior/regression checks for the actual changed surface. Exercise the changed runtime path as specified by IMPLEMENTATION.md, including assigned macro flows with their prescribed real participants. For a direct change, complete the entire change and obtain final combined regression/runtime evidence before requesting Pass. After fixes, renew evidence for the resulting code. Keep exact commands/scenarios, outcomes, coverage limits, and current code identity available; planned or historical results are not current proof.

Check the complete unit result against its cited design and acceptance conditions before dispatching review. This is conformance checking, not a new architecture choice. A ticket may distinguish its usable increment from flows explicitly owned by a later ticket. A direct change must satisfy its entire target and all local, macro-flow, and final-conformance obligations now. An assigned flow that cannot run is a blocker, not work to defer past release or joint-integration handoff.

Before requesting review, save the implementation/repair decision and fresh evidence under the shared record contract, including exact source/code revisions and material observed results. Task output or transient agent links alone are not durable evidence.

## 5. Obtain independent conformance review

At first review use a separate read-only reviewer context and bind its handle to this unit. In delegated mode send the package to the controller, which creates or resumes the bound reviewer; do not create a competing role. In standalone mode dispatch and retain the reviewer directly. Supply reviewer-prompt.md and its route-appropriate required inputs, the complete current unit change and code basis, affected surrounding code/callers, source approvals, repository rules, IMPLEMENTATION.md, and actual verification evidence. Keep private author reasoning separate. A role switch in the author context is not independent review.

Include governing owners `implement-unit` and `workflow-artifacts`, complete current standards/reviewer instructions or verified resolved installed resources, the target repository/checkout and work identity, WORKFLOW-ARTIFACTS.md, work entry and owning-log references, stable open finding IDs, relevant repair/decision records, exclusion evidence, and original role/recovery state. Mark skill loading reference-only and the assignment independent read-only review, not implementation. Reviewers inspect these read-only; the controller or standalone author records their reports.

Require an identifiable current snapshot and complete `Pass`, `Changes required`, or `Blocked`. Return implementation findings to the original implementer, renew affected verification, and return changes, finding dispositions, current code identity, and evidence to the original reviewer. Repeat automatically until the full current unit scope passes without unresolved issues, including affected interactions outside previous findings. Reuse unchanged sources by reference; full-scope reassessment needs neither a fresh agent nor mechanical rereading. Route genuine upstream defects or unavailable prerequisites through the controller or, standalone, to the user; do not rotate roles or ask the human to supervise ordinary repairs.

Save each returned report—including `Changes required` or `Blocked`—before repair or gate advancement. Preserve its actual verdict, checks, limits, and exact reviewed basis. Record repairs as addressed/awaiting review; only the reviewer confirms closure or withdrawal. Persist the new disposition and current state before handoff; update `issue.md` through its owner before blockers, role replacements, or session/stage transitions.

## 6. Hand off the reviewed result and stop

After a current independent Pass with no unresolved findings or blockers, persist the verdict and current state, then return implemented scope, current code basis, source references, actual verification/limits, and record links. In delegated mode return the reviewed unit to the controller without per-unit human approval or a whole-work `delivery.md`. In standalone mode, after verification and Pass but before requesting explicit human acceptance, write `.scratch/<work-slug>/delivery.md` under the shared summary contract. A standalone ticket identifies only its reviewed scope, never claims whole-set delivery, and must preserve any broader existing summary. For a direct change this full-change Pass, including final combined runtime evidence, is the final independent review; do not add a duplicate overall review. Neither mode authorizes starting another unit.

Retain the pair's handles and recoverable state for later conformance repairs during this implementation. A repair or relevant baseline change invalidates affected review/evidence and any acceptance; obtain renewed verification and full-scope reassessment by the original reviewer. Before resuming edits, inspect the current code basis and intervening changes instead of restoring an old version from memory. Replacement and handoff follow IMPLEMENTATION.md; do not silently create a fresh implementer or reviewer.

For standalone acceptance, persist the actual user decision with exact scope/basis in the owning log; update the work entry and summary afterward. Renew affected evidence/review and integrate the summary before a repaired-result acceptance request. Retain excluded artifacts; do not publish, commit, or delete the records on completion.

Do not automatically commit, merge, push, close remote issues, or release. The existing `implement` controller owns final human acceptance; real ticket sets also require combined verification and an independent overall review. A ticket-local Pass does not prove whole-set completion, and no Pass grants human acceptance. Standalone use needs no orchestrator; delegated use returns to the supplied controller without recursively loading or executing it. Post-delivery design questions belong to `clarify-change`, loaded by name only for authorized upstream work; this skill executes its approved result rather than governing the design.
